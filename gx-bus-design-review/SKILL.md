# GX 双总线产品设计审查

## 目标

在产品设计阶段审查智能体方案是否符合“AI 总线 + 业务总线 + 业务底座”模式。不要代写完整 PRD，重点判断方案能不能接入 [[GXClaw]]、[[业务总线]] 和 [[业务底座]]，以及是否存在后期必然重构的架构越界。

内部标识：`agent_boundary`、`intent_map`、`skill_candidates`、`bus_dependencies`、`fact_model`、`deliverables`、`PASS / CONDITIONAL / FAIL`。

引用降级：`wikilink_fallback`。如果 `[[GXClaw]]`、`[[业务总线]]`、`[[业务底座]]` 等 wikilink 页面不可读，不要停止审查；以本文件内置的分层边界、红线和评分规则作为最低判定标准。用户额外提供原始规范时，优先按原始规范校正。

## 输入

优先读取用户提供的材料，不默认读取代码。

必需输入：

- 产品目标：智能体要解决的业务问题。
- 目标用户：使用者角色、业务职责、专业背景。
- 业务域：如设备、采矿、边坡、排水、申报、质检。
- 业务流程：从用户请求到业务结果交付的完整流程。
- 业务系统清单：涉及的 ERP、MES、EAM、GIS、财务、生产等系统。
- 数据对象：涉及的实体、状态、关系、事件、指标、规则结果。

强烈建议输入：

- 用户 query 样例：至少 10 条，理想状态为 20-50 条真实 query。
- PRD、原型、流程图、接口草案。

缺少关键信息时，先基于现有材料给出“有条件审查”，只问一个最关键的补充问题。

## 工作流

### 1. 判断业务域边界

检查 Agent 是否按业务域拆分，而不是按功能拆分。

判断标准：

- 知识边界是否独立。
- 用户群体是否独立。
- 工作流是否能在该 Agent 内完成主要闭环。

至少两项成立，才建议独立为一个 Agent。

输出：

- `agent_boundary`：建议的 Agent 边界。
- 是否需要拆分多个 Agent。
- 当前拆分是否存在“功能型 Agent”反模式。
- `agent_merge_target`：不满足独立 Agent 条件时，必须说明应合并到哪个业务域 Agent，以及哪些能力应改为 Skill。

### 2. 构建意图图谱

基于用户 query 和业务流程归纳主要意图。

输出：

- `intent_map`：用户 query -> 意图 -> 所需 Skill -> 返回结果。
- 每类意图的必要输入字段。
- 需要人工确认的分支。
- 无法落到明确 Skill 的模糊意图。

### 3. 审查 Skill 候选清单

检查每个 Skill 是否只做一件明确、可复用的事情。

Skill 类型：

- 数据查询型：只读，返回结构化数据。
- 数据操作型：写入或修改，有副作用。
- 计算分析型：输入数据，输出分析结果。
- 内容生成型：输出非结构化内容。
- 外部调用型：调用第三方或业务系统能力。

输出：

- `skill_candidates`：Skill 候选清单。
- 每个 Skill 的职责边界、参数草案、返回结构草案、错误码草案。
- 过大、过泛、不可复用的 Skill。
- `reusable_skill_map`：跨 Agent 复用能力清单。凡是两个及以上 Agent 可能共同使用的能力，应建议拆为独立 Skill；如果能力只服务单一业务域，也要说明为什么不独立复用。

### 4. 识别业务总线依赖

判断哪些 Skill 需要通过业务总线编排，不能直接调用系统。

业务总线应负责：

- 多系统调用顺序编排。
- 协议适配。
- 专用算法、专用模型、专用知识库编排。
- 错误重试、超时控制、日志和结果聚合。
- 人机协作节点、流程状态推送。

输出：

- `bus_dependencies`：业务总线编排点清单。
- 专用能力需求。
- 业务系统适配需求。
- 人机协作与工作流可视化需求。

### 5. 设计业务底座事实模型

识别智能体需要依赖的稳定业务事实。

事实类型：

- 实体：矿山、设备、荒料、边坡、人员等。
- 状态：运行、风险、审批、质量等。
- 关系：归属、影响、依赖、流转等。
- 事件：报警、检测、审批、维修等。
- 指标：产量、能耗、风险值、稼动率等。
- 规则结果：阈值命中、校验结论、风险等级等。

接口判断：

- 事实查询和关系查询通常是基础接口。
- 状态订阅只在前端或流程需要感知事实变化时要求。
- 事实更新只在业务总线完成流程后需要写入智能体可用事实时要求。
- 不要把所有接口机械判为必需。

输出：

- `fact_model`：业务底座事实模型草案。
- 事实查询、关系查询、状态订阅、事实更新的场景化建议。
- 业务底座与业务系统的边界说明。

### 6. 扫描反模式

命中以下任一项，结论直接不通过：

- Agent 直接调用 ERP、MES、EAM、GIS 或数据库。
- Agent 按查询、审核、生成等功能拆分，而不是按业务域拆分。
- Skill 承担复杂业务流程编排。
- Skill 绕过业务总线直接调用业务底座。
- 业务底座直接面向 Agent 或 Skill 暴露。
- 业务底座承载专用算法、专用模型、专用知识库。
- 业务系统直接面向智能体暴露零散接口。
- Skill 调用参数不是结构化 JSON。

### 7. 检查文档交付物

检查产品设计是否规划以下交付物：

- `agent.md`：角色、工作流、约束、兜底策略。
- `skill.md`：功能、参数、实现、返回、错误码。
- API 文档：业务总线接口、业务底座事实接口、业务系统适配接口。
- 业务总线编排图：专用能力调用、事实查询、系统适配、人机协作节点。
- 业务底座事实模型文档：实体、状态、关系、事件、指标、规则结果。
- 工作流可视化与人机协作文档：流程节点、人机协作节点、状态推送协议。
- 测试用例：覆盖主要意图和边界场景。

输出：

- `deliverables`：缺失交付物和建议补齐顺序。

## 评分

| 模块 | 权重 |
| --- | ---: |
| Agent 边界 | 15 |
| 意图图谱 | 15 |
| Skill 设计 | 15 |
| 业务总线依赖 | 20 |
| 业务底座事实模型 | 15 |
| 文档交付物 | 10 |
| 层级边界 | 10 |

结论规则：

- 90-100：通过。
- 75-89：有条件通过。
- 60-74：不建议进入开发。
- 0-59：不通过。
- 命中红线：不看分数，直接不通过。
