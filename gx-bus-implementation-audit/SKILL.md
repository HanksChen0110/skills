# GX 双总线实现审计

## 目标

在开发、联调、测试、验收或上线前审计项目是否真正打通“AI 总线 + 业务总线 + 业务底座”。重点不是看文档像不像，而是看代码、配置、Skill、接口、日志和测试证据是否能证明真实链路成立。

内部标识：`project_stage`、`bus_url_scan`、`skill_contract`、`fact_api`、`e2e_trace`、`doc_completeness`、`PASS / CONDITIONAL / FAIL`。

## 输入

必需输入：

- 项目代码路径。
- 当前项目阶段：本地验证、联调准备、测试验收、上线前。

优先输入：

- Agent 配置，如 `agent.md` 或同类配置。
- Skill 配置，如 `skill.md`、Manifest、schema。
- 环境配置，如 `.env.example`、配置文件、部署参数。

输入降级：`input_fallback`。如果 Agent、Skill 或环境配置没有明确提供，先从代码路径、目录命名、Manifest、配置样例、部署脚本和测试日志中推断；仍无法确认时，将该项标记为“无法判定”，并列入 P1 或 P2。只有在测试验收或上线前阶段缺少真实链路证据、业务总线配置证据或命中红线时，才直接判 P0 / FAIL。

分阶段输入：

- 业务总线 API 文档：联调准备阶段强烈建议，测试验收和上线前阶段必需。
- 业务底座接口文档：联调准备阶段强烈建议，测试验收和上线前阶段必需。
- 测试用例 / 日志：本地验证阶段可选，联调准备阶段强烈建议，测试验收和上线前阶段必需。

## 工作流

### 1. 确认项目阶段

先判断 `project_stage`，再决定审计严苛度。

| 阶段 | mock 容忍度 | 判断 |
| --- | --- | --- |
| 本地验证 | 允许 | 必须明确标记为 mock，不能伪装成真实业务总线 |
| 联调准备 | 有条件允许 | 必须已有真实或沙箱业务总线配置位、切换方式、接口映射文档 |
| 测试验收 | 原则上不允许 | 除非接口未就绪且有临时豁免说明 |
| 上线前 | 不允许 | 双总线路径中发现未解释 mock 即不通过 |

### 2. 检查 AI 总线接入

检查项：

- 是否有明确 `agent_id`。
- 是否有会话标识，如 `session_key`。
- 是否有 Skill Registry 或 Manifest。
- 是否有权限、鉴权、调用范围约束。
- 是否能说明用户请求如何路由到目标 Agent。

### 3. 检查 Agent 层边界

Agent 只应做意图识别、业务域工作流、Skill 路由和结果组织。

红线：

- Agent 直接查数据库。
- Agent 直接调用 ERP、MES、EAM、GIS。
- Agent 承担协议转换、系统适配或复杂业务编排。

### 4. 检查 Skill 契约

检查 `skill_contract`：

- 参数 schema 是否明确。
- 返回结构是否统一。
- 是否有错误码。
- 是否有超时设置。
- 是否有权限要求。
- 是否以 JSON 向业务总线传输。
- 是否把自然语言传到 Skill 下层。
- `json_boundary_trace`：抽查 Skill -> 业务总线、业务总线 -> 业务底座、业务总线 -> 业务系统适配器的调用证据，确认 Skill 层以下不传递自然语言描述，而是传递 JSON、Graph Query、事件订阅或明确协议数据。

红线：

- Skill 调用参数不是结构化 JSON。
- Skill 内部承担多系统流程编排。

### 5. 扫描业务总线真实接入

执行 `bus_url_scan`。优先使用 `rg` 或仓库现有搜索工具扫描：

```text
localhost
127.0.0.1
mock
stub
fake
demo
BUS_BASE_URL
BUS_MODE
BUS_ENV
```

扫描范围：`scan_scope`。优先扫描生产代码、运行时配置、部署配置、Agent/Skill 配置、Manifest、接口适配层和 CI 生成的运行参数。测试代码、示例文档、历史日志只作为佐证，不因关键词命中直接判红线。

排除目录：`exclude_dirs`。默认排除或降级处理 `.git`、`node_modules`、`dist`、`build`、`coverage`、`.cache`、临时目录、第三方依赖目录、截图或导出文件。除非这些目录中的命中会被实际部署或运行加载，否则不计入 P0。

命中分级：

- P0：测试验收或上线前阶段，真实双总线路径中的生产代码、运行配置或部署参数仍指向未解释的 `localhost`、`127.0.0.1`、`mock`、`stub`、`fake`、`demo`。
- P1：联调准备阶段缺少真实或沙箱业务总线配置位、切换方式、接口映射，或本地残留有责任人但无替换时间。
- P2：只出现在测试 fixtures、文档示例、注释说明、历史日志中的关键词命中。

检查项：

- 业务总线地址是否来自统一配置，而不是写死在代码或 Skill 中。
- 是否明确区分 `mock`、`sandbox`、`real`。
- 测试验收或上线前阶段是否已切换到真实或沙箱业务总线。
- 发现本地残留时，是否有缺口说明、责任人和预计替换时间。

建议配置：

```text
BUS_MODE=mock | sandbox | real
BUS_BASE_URL=https://...
BUS_ENV=local | test | staging | production
```

### 6. 检查业务底座事实接口

检查 `fact_api`：

- 事实查询接口。
- 关系查询接口。
- 状态订阅接口。
- 事实更新接口。
- 实体、状态、关系、事件、指标、规则结果命名是否稳定。

阶段性判断：

- 事实查询和关系查询通常是基础能力。
- 状态订阅只在前端或流程需要感知事实变化时要求。
- 事实更新只在业务总线完成流程后需要写入智能体可用事实时要求。

接口质量检查：`fact_api_quality`。

- 幂等性：相同参数重复调用，查询类结果一致；操作型 Skill 相关写入不得重复造成副作用。
- 可观测性：返回或日志中能看到执行耗时、影响范围、错误码和必要调试信息。
- 降级能力：下游系统不可用时返回明确错误码，不挂死、不让 Agent 猜测。
- 版本兼容：接口升级有版本号或兼容策略，验收 / 上线前不得只依赖临时字段。
- 本体一致性：实体、关系、状态、事件、指标字段命名稳定，不随单个业务系统字段频繁漂移。

红线：

- 业务底座直接面向 Agent 或 Skill。
- 业务底座执行专用算法、模型或知识库检索。
- 业务底座替代业务系统事务流程。
- 测试验收或上线前阶段，核心事实接口缺少降级错误码、可观测日志或稳定字段命名。

### 7. 检查专用能力编排

专用算法、专用模型、专用知识库应归业务总线编排。

检查项：

- Skill 是否绕过业务总线直连算法服务。
- Skill 是否绕过业务总线直连 RAG 或知识库。
- 业务总线是否能按 Skill 参数选择不同编排路径。
- 业务总线是否聚合事实数据、模型结果、知识依据和系统适配结果。

### 8. 验证端到端链路

按项目阶段要求检查 `e2e_trace`：

- 本地验证：允许 mock 链路，但必须标记。
- 联调准备：至少提供真实或沙箱业务总线接口映射与配置证据。
- 测试验收 / 上线前：必须至少验证一条真实链路。

标准链路：

```text
用户请求
  -> AI 总线
  -> Agent
  -> Skill
  -> 业务总线
  -> 业务底座 / 业务系统
  -> 业务总线聚合结果
  -> Skill 格式化
  -> Agent 生成回复
```

证据要求：

- `trace_id`。
- 执行耗时。
- 业务总线执行路径，如 `fact_query`、`model_call`、`system_adapter`。
- 成功返回或明确错误码。
- 日志中能区分 AI 总线、Skill、业务总线、业务底座、业务系统。
- 响应时间、错误率、返回格式正确性记录。

工作流与人机协作验证：`workflow_e2e`。如果项目包含审批、确认、补充信息、流程暂停或状态推送，端到端证据还必须覆盖：

- 业务总线生成流程节点状态。
- 前端或调用方能收到状态推送，如 WebSocket、SSE、Webhook 或轮询结果。
- 人工输入能通过业务总线回调继续流程。
- 日志能串起暂停、等待、回调、继续执行和最终返回。
- 业务底座只提供事实变化或事实更新，不直接控制前端或驱动流程。

### 9. 检查配套文档完整性

检查 `doc_completeness`：

- `agent.md`：角色、工作流、约束、兜底策略。
- `skill.md`：功能、参数、实现、返回、错误码。
- API 文档：业务总线接口、业务底座事实接口、业务系统适配接口。
- 业务总线编排图：专用能力调用、事实查询、系统适配、人机协作节点。
- 业务底座事实模型文档：实体、状态、关系、事件、指标、规则结果。
- 工作流可视化与人机协作文档：流程节点、人机协作节点、状态推送协议。
- 测试用例：覆盖主要意图和边界场景。

### 10. 输出整改清单

按优先级输出：

- P0：阻塞双总线真实接入、命中红线、验收阶段仍靠 mock 的问题。
- P1：影响稳定性、可观测性、测试验收的问题。
- P2：建议优化项。

## 评分

| 模块 | 权重 |
| --- | ---: |
| AI 总线接入 | 10 |
| Agent 边界 | 10 |
| Skill 契约 | 15 |
| 业务总线接入 | 20 |
| 本地残留 | 15 |
| 业务底座 | 15 |
| 可观测性 | 10 |
| 端到端测试 | 5 |

结论规则：

- 90-100：通过。
- 75-89：有条件通过。
- 60-74：不建议进入下一阶段。
- 0-59：不通过。
- 命中红线：不看分数，直接不通过。
- 阶段红线优先于评分权重：`stage_gate_over_score`。测试验收或上线前缺少至少一条真实或沙箱端到端链路时，即使端到端测试只占 5 分，也必须按阶段红线输出 FAIL 或 CONDITIONAL，不得用高总分掩盖。
