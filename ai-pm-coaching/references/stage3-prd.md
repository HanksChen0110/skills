# 第三阶段 PRD与原型

## 阶段目标

把项目从“方向成立、分析成立”推进到“系统成立”：PRD 能指导协作团队落地，Harness 能约束模型和工具，vibe coding 原型能实际跑通一条 P0 主链，并留下输入输出、失败处理、Trace 与评测证据。章节齐全、界面好看和技术名词都不能替代运行证据。

## 结论口径

| 结论 | 触发条件 |
| --- | --- |
| **推进** | 业务目标与 P0 清楚；主 Workflow、状态、AI 节点 I/O、边界、评测和人工责任一致；MVP Harness 七项通过；原型跑通成功与失败样本并留证据 |
| **收束** | 核心方案成立，但范围过大、部分 Harness 层仅有设计、原型只覆盖展示路径或评测证据不足 |
| **换题或重做** | PRD 与前两阶段结论断裂；关键数据/工具不可得；AI 必要性不成立；原型不能运行；高风险动作无人审；学员无法解释关键设计 |

## 证据检查

按以下顺序检查，不逐页念 PRD：

1. 业务问题、目标用户、基线、目标、P0 和非目标。
2. Before / After Workflow、角色权限、状态机和最终交付标准。
3. 每个 AI 节点的输入、输出、Schema、校验、异常和 fallback。
4. 规则、RAG、LLM、Agent、工具和人工的分工及选择依据。
5. 数据、知识、规则资产的来源、owner、更新、版本、权限与删除。
6. 低置信度、无结果、冲突、超时、越权、结构错误与人工接管。
7. 标准答案、评测样本、指标、分母、基线、阈值与标注责任。
8. Bad Case 分类、修复对象、回归集和发布门槛。
9. Trace 中的任务 ID、模型/Prompt、工具输入输出、资料版本、规则命中、人工修改、耗时与成本。
10. vibe coding 原型的启动方式、真实调用、成功/失败输入输出、原始错误与重跑证据。
11. 学员本人主导的关键判断，以及 AI 生成但未核验的内容。

## 八组追问

### 1. 业务目标与范围

- “服务谁、解决什么问题，基线与目标分别是什么？”
- “P0 只验证哪条主链，明确不做什么？”
- “哪些需求来自真实证据，哪些仍是假设？”
- “什么结果意味着继续、收束或停止？”

### 2. Workflow、角色与状态

- “用一个真实样本走完 Before / After Workflow。”
- “每个节点的进入条件、负责人、输出与验收是什么？”
- “提出者、使用者、审核者和最终决策者各有什么权限？”
- “超时、失败、人工接管后如何回退与恢复？”

### 3. AI 适配与架构

- “为什么必须用 AI，不用规则或固定 Workflow 为什么不行？”
- “主原型是什么，选择依据是什么？”
- “模型、RAG、工具和编排的备选方案如何比较？”
- “移除 Agent 自主规划后，固定 DAG 或状态机能否更可靠？”

### 4. Context、数据与工具

- “上下文如何选择、压缩、隔离、保存和恢复？”
- “数据、知识和规则由谁更新，冲突与过期如何处理？”
- “工具/API 是否真实调用，参数 Schema、权限和错误码是什么？”
- “哪些数据不得进入模型，保存多久，如何删除？”

### 5. 编排、边界与人审

- “任务如何拆分、路由、重试、停止和失败回跳？”
- “预算用完时如何停止或降级？”
- “哪些动作必须人审，人工看什么证据？”
- “发生越权、误发或错误执行时如何隔离、回滚和追责？”

### 6. 评测与可观测性

- “标准答案、样本、指标、分母、基线和阈值是什么？”
- “谁标注、谁验收，指标冲突如何决策？”
- “一次任务能否追到模型、Prompt、资料、工具和人工修改？”
- “Bad Case 如何分类，修复后如何进入回归和发布判断？”

### 7. vibe coding 原型

- “现在能否启动原型并完成一次 P0 任务？”
- “调用的是真实工具/API、受控模拟，还是写死的演示？”
- “成功、边界和失败样本留下了哪些输入输出与日志？”
- “失败时是否诚实展示错误、降级或人工接管？”
- “原型暴露了什么文档未想到的问题，改了什么？”

### 8. 成本、上线与 Ownership

- “单次任务的模型、检索、工具、人工与存储成本如何估算？”
- “时延、并发、稳定性和合规到什么门槛才可试点？”
- “灰度、监控、停止、回滚和事故责任如何定义？”
- “哪三项关键判断由你主导，AI 的架构或代码如何验证？”
- “关掉 AI 后，能否解释一个失败样本为何发生、应改哪层？”

## MVP Harness 七项硬门

任何一项完全缺失都构成当前阶段阻断；“后续会补”不能通过。

| 门槛 | 最低通过证据 |
| --- | --- |
| **Task Spec** | 真实任务的目标、输入、输出、成功条件和不做项明确 |
| **Plan-Execute-Verify** | 计划、执行、结果校验可观察；校验失败会阻断交付 |
| **Tool/API Access** | 至少一个关键工具/API 真实可用，或有受控模拟及替换条件 |
| **Permission/Human Review** | 最小权限、人工确认点、最终责任人和禁止动作明确 |
| **Trace/Run Record** | 一次运行可追到任务、版本、节点输入输出、工具结果、人工修改和耗时 |
| **Result Verification** | 有标准答案或可执行验收规则，能判定结果是否通过 |
| **Failure Capture** | 失败被记录、分类，并有回跳/接管与重跑条件 |

## 九层 Harness 评分

分档：0 分无正文或证据；1 分只有名词、清单或计划；2 分已有机制和部分证据，但异常、恢复、评测或真实运行不完整；3 分机制可执行，成功与失败都有运行、Trace、验收和回归证据。设计但未运行的层最高 2 分。

必须使用以下原名与表头：

| Harness层 | 分数 | 已有证据 | 主要缺失 |
| --- | ---: | --- | --- |
| Interaction 任务交互 |  |  |  |
| Context 上下文 |  |  |  |
| Tool 工具 |  |  |  |
| Memory / State 记忆与状态 |  |  |  |
| Orchestration 编排 |  |  |  |
| Execution / Sandbox 执行边界 |  |  |  |
| Evaluation / Feedback 评测反馈 |  |  |  |
| Observability 可观测性 |  |  |  |
| Governance / Safety 治理安全 |  |  |  |

## 四个闭环

链路文字和顺序不得改写：

- 任务闭环：`识别 -> 查询 -> 检索 -> 审核 -> 初稿 -> 发送`
- 上下文闭环：`选择 -> 压缩 -> 保存 -> 人工接管 -> 恢复`
- 工具闭环：`选择 -> 参数校验 -> 执行 -> 异常处理`
- 评估闭环：`标准答案 -> 指标阈值 -> 离线测试 -> 失败分类 -> 回归集 -> Prompt/RAG/Harness更新`

必须用失败样本检查四条链。每个断点写明失败现象、停在哪一步、谁接管、如何恢复、修复对象、重跑条件和回归结果。

## vibe coding 最低标准

目标不是还原完整产品，而是让一条 P0 主链真实接收输入、执行规则/模型/工具、输出结果、暴露错误并留下运行记录。

最低证据：

- 可复现的启动命令或步骤、代码版本与依赖说明。
- 至少一个关键工具/API 真实接入；不能接入时明确受控模拟边界和替换条件。
- 一个成功样本、一个边界或失败样本的原始输入输出。
- Trace、截图、耗时、错误信息和人工接管记录。
- 原型暴露的问题，以及据此回改的 PRD 内容。

硬编码页面、静态演示数据、只展示截图或吞掉错误，都不能算可跑原型。

## 报告骨架

严格按以下顺序输出：

1. **结论**：推进 / 收束 / 换题或重做；一句话判据与硬阻断项。
2. **已扎实部分**：业务范围、系统机制、原型运行、评测风险和本人判断。
3. **完整性检查**：目标/范围、Workflow、角色/状态、AI I/O、数据资产、评测门槛、可跑原型；列证据、缺口与判断。
4. **关键问题**：只列 1-3 个最大问题；写证据、影响、修复动作与验收方式。
5. **AI能力与架构问题**：主原型、规则/RAG/LLM/Agent/工具/人审分工、状态编排、数据/时延/成本取舍。
6. **Harness门槛**：七项逐条给证据、通过/阻断与补齐动作。
7. **九层评分**：使用固定表头和九层原名，不把计划算实现。
8. **四个闭环**：逐条写当前链路、断点、接管、恢复与回归。
9. **认知偏误**：偏误、作业表现、点破与修正。
10. **Now-Next-Later**：Now 只放阻断真实交付或风险红线的事项。
11. **当面追问**：问题及合格回答应包含的证据。
12. **AI PM结论**：已证明、尚不能证明、本人关键决策与进入下一阶段的条件。

## 阶段交付门槛

- 业务问题、目标、P0 与非目标一致。
- Before / After Workflow 能用真实样本走通。
- 角色、权限、状态、超时、回退与恢复明确。
- 关键 AI 节点有输入、输出、Schema、校验、异常和 fallback。
- 数据、知识、规则资产可追溯、可更新、可控权。
- MVP Harness 七项全部有证据。
- vibe coding 原型能启动并跑通成功与失败样本。
- 九层按 0-3 分评分，设计与运行证据分开。
- 四个闭环的断点已经分级和指派修复动作。
- 评测集、指标、分母、基线、阈值、标注人与回归集明确。
- 成本、时延、隐私、合规、灰度、停止与回滚条件明确。
- 学员能讲清三项本人决策、被否方案及证据。
