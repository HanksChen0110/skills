# 第三阶段 PRD与原型

## 阶段目标

把项目从“方向成立、分析成立”推进到“产品与系统同时成立”：用用户体验五层检查产品定义与交互，用 ICTSOEVMG Harness 九要素约束 AI 系统；若出现 Agent，先完成“系统边界 → 控制模式 → Agent 拓扑”的判型，再决定是否进入 P0。PRD 和 vibe coding 原型必须跑通一条 P0 主链，并留下输入输出、失败处理、Trace 与验证证据。章节齐全、界面好看和技术名词都不能替代运行证据。

## 原有 PRD 完整性审核（不可被 Agent 判型替代）

Agent 判型是新增的一层判断，不替代原来的 PRD 审核。每次第三周陪跑先按下面顺序检查，只有产品定义和 PRD 主链成立后，才进入 Agent 复杂度讨论：

| 审核面 | 必须确认的内容 |
| --- | --- |
| 产品目标与范围 | 目标用户、真实问题、业务目标、成功指标、P0、非目标和不做项 |
| 用户与业务流程 | Before / After Workflow、任务入口、输入、输出、角色、责任、状态和人工接管 |
| 功能与交互 | 功能清单、页面/交互、澄清、确认、修改、状态反馈、异常提示和交付完成标准 |
| AI 节点定义 | 每个模型、RAG、规则、Tool 或 Agent 节点的输入、输出、Schema、校验、异常和 fallback |
| 数据与系统约束 | 数据/知识/规则来源、owner、版本、权限、更新、删除、接口、时延、成本和安全 |
| 验收与运营 | 标准答案、样本、指标、分母、基线、阈值、Bad Case、回归、Trace、监控、发布和回滚 |
| 原型与证据 | 启动步骤、真实调用或受控模拟、成功/边界/失败样本、原始错误和修订记录 |

材料缺一项不代表立即换题，但必须标明“已确认缺失”或“材料未提供”，给出补齐动作和进入条件。Agent 判型不能把缺失的用户、功能、验收和运行证据盖住。

## 产品方向框架的用法

使用 `product-directions.md` 核对主方向及其适用拼图，把已选 P0 能力落到 PRD 节点、数据与接口、权限、异常处理和验收证据。逐项区分有运行证据、仅有设计、已确认缺失与材料未提供；不要求后续或不适用组件进入 P0，也不把架构图当运行证明。

两种产物均在阶段预判中给方向与依据，核心产物用一行列参考组合；将最多 3 项关键拼图缺口合入双框架缺口表，关联真实节点、Harness、体验层、补齐动作与回归验收，不另加一套长报告。

## Agent 架构判型与 Harness 连接

只要 PRD 或原型出现 Agent、Agentic Workflow 或 Multi-Agent，先做判型再做实现建议。判型对象必须先写清 **System Boundary**，例如“一个调研节点”还是“整条营销平台主链”；同一系统在不同边界下可以得到不同结论。

| 判型步骤 | 必须回答的问题 | 结论标签 |
| --- | --- | --- |
| 1. 控制模式 | `Next Action` 谁决定？宏观流程是否固定？能否根据反馈 `Replanning`？谁判断 `Termination`？ | `AI Workflow` / `Agentic Workflow` / `Agent` |
| 2. Agent 拓扑 | 是否有两个以上独立决策循环？是否有 `Independent Boundary`、`Specialization` 和 `Coordination`？ | `Single-Agent` / `Multi-Agent` |
| 3. 复杂度取舍 | 移除 Agent 自主规划后，固定 Workflow、状态机或人工能否可靠完成 P0？ | 选择可靠解决问题的最低复杂度架构 |

判型不能由“用了 LLM、Tool、循环、多个 Prompt 或多个模型”直接推出。固定顺序的多个 LLM 节点是 Multi-step Workflow；多个 Agent 只有在存在独立职责和委派、交接、共享状态、协商或监督等协调关系时才算 Multi-Agent。判型结果必须接入双框架缺口表：重点检查 Orchestration、State / Memory、Tool、Verification、Monitoring、Governance；证据不足时写“判型候选，待验证”，不把 Agent 当作默认答案。

## 结论口径

| 结论 | 触发条件 |
| --- | --- |
| **推进** | 业务目标与 P0 清楚；主 Workflow、状态、AI 节点 I/O、边界、评测和人工责任一致；MVP Harness 七项通过；原型跑通成功、边界与失败三类样本并留证据 |
| **收束** | 核心方案成立，但范围过大、部分 Harness 层仅有设计、原型只覆盖展示路径或评测证据不足 |
| **换题或重做** | PRD 与前两阶段结论断裂；关键数据/工具不可得；AI 必要性不成立；原型不能运行；高风险动作无人审；学员无法解释关键设计 |

## 分环节主持重点

### PRD 完整性与 AI 节点

- **导师判断**：PRD 是否真正定义了 AI 节点的 I/O、状态、边界和验收，而不只是功能名称。
- **导师讲解**：AI PRD 的核心是约束不确定性；每个节点都要说明 Context、规则/模型/工具/人工分工、结构校验和 fallback。
- **未通过处理**：缺 I/O 或验收时不讨论模型选型；新增功能无前序证据时移出 P0。

### Agent 架构判型

- **导师判断**：学员是否把“需要模型”误写成“需要 Agent”，是否把多个 Prompt 或多个模型误写成 Multi-Agent；系统边界、运行时决策权和 P0 复杂度是否一致。
- **导师讲解**：先写 `System Boundary`，再按 `Next Action → Replanning → Termination` 判断控制模式；若涉及多个 Agent，再检查 `Independent Boundary → Specialization → Coordination`。控制模式和 Agent 拓扑是两个维度，Multi-Agent 不是比 Agent 更高级的默认阶段。
- **必须落到 PRD 的字段**：每个 Agent 的目标/责任、Instructions、Context、State、Toolset、Decision Loop、交接或共享状态、停止条件、权限与人工接管；系统级还要写 Orchestrator 或 Workflow 的边界。
- **与 Harness 的连接**：Agent 自主规划增加的不是一句“更智能”，而是 Orchestration、State / Memory、Tool、Verification、Monitoring、Governance 的新增约束。只要固定 DAG、状态机或人工能稳定完成 P0，就优先保留更简单的方案。
- **未通过处理**：缺少六个判型证据时写“判型候选，待验证”；无法证明独立决策时降级为 Workflow、Agentic Workflow 或 Single-Agent，不把 Multi-Agent 放进 P0。

### 原型实跑

- **导师判断**：原型是否真实执行；错误是否可见；工具、权限、人审和状态是否按设计工作。
- **导师讲解**：静态页面和写死数据只能证明交互外观，不能证明 AI 产品链路；失败样本比一次成功演示更能暴露 Harness 缺口。
- **未通过处理**：保留原始错误，标记失败层、接管动作和最小重跑条件，不替学员描述“理论上可行”。

### Harness、评测与闭环

- **导师判断**：七项硬门是否有运行证据；九层分数是否虚高；失败是否进入 Trace、分类、修复和回归。
- **导师讲解**：Harness 不是附加文档，而是模型周围可执行的控制系统；评测必须连接版本决策。
- **未通过处理**：任一硬门完全缺失即阻断；只有设计的层最高 2 分；没有回归证据不进入发布判断。

### 收尾

- **导师判断**：学员是否能解释自己的三项关键取舍和一个失败样本。
- **导师讲解**：AI PM 对业务目标、技术选择和风险证据负责，不以术语数量或页面完成度证明能力。
- **未通过处理**：按缺口退回方向、竞品或执行环节，明确下一次只验哪些证据。

## 证据检查

按以下顺序检查，不逐页念 PRD：

1. 业务问题、目标用户、基线、目标、P0 和非目标。
2. Before / After Workflow、角色权限、状态机和最终交付标准。
3. 每个 AI 节点的输入、输出、Schema、校验、异常和 fallback。
4. 规则、RAG、LLM、Agent、工具和人工的分工及选择依据。
5. 数据、知识、规则资产的来源、owner、更新、版本、权限与删除。
6. 低置信度、无结果、冲突、超时、越权、结构错误与人工接管。
7. 标准答案、评测样本、指标、分母、基线、阈值与标注责任。
8. Bad Case 分类、修复对象、回归集和发布门槛。
9. Trace 中的任务 ID、模型/Prompt、工具输入输出、资料版本、规则命中、人工修改、耗时与成本。
10. vibe coding 原型的启动方式、真实调用、成功/边界/失败输入输出、原始错误与重跑证据。
11. 学员本人主导的关键判断，以及 AI 生成但未核验的内容。

## 可选追问

问题优先检查 AI 系统机制、验证和 Ownership；业务信息只确认目标、输入输出、责任和风险约束。

### 1. 任务目标与 AI 约束

- “请用一个真实样本说明任务输入、目标输出、验收人和成功条件。”
- “P0 只验证哪条主链，明确不做什么？”
- “哪些需求来自真实证据，哪些仍是假设？”
- “什么结果意味着继续、收束或停止？”

### 2. Workflow、角色与状态

- “用一个真实样本走完 Before / After Workflow。”
- “每个节点的进入条件、负责人、输出与验收是什么？”
- “提出者、使用者、审核者和最终决策者各有什么权限？”
- “超时、失败、人工接管后如何回退与恢复？”

### 3. AI 适配与架构

- “为什么必须用 AI，不用规则或固定 Workflow 为什么不行？”
- “主原型是什么，选择依据是什么？”
- “模型、RAG、工具和编排的备选方案如何比较？”
- “本次判断的 System Boundary 是什么？下一步由谁决定，失败后能否 Replanning，谁判断 Termination？”
- “如果有多个 Agent，各自的 Independent Boundary、Specialization、Coordination 证据是什么？”
- “移除 Agent 自主规划或 Multi-Agent 协作后，固定 DAG、状态机或单 Agent 能否更可靠地完成 P0？”

### 4. Context、数据与工具

- “上下文如何选择、压缩、隔离、保存和恢复？”
- “数据、知识和规则由谁更新，冲突与过期如何处理？”
- “工具/API 是否真实调用，参数 Schema、权限和错误码是什么？”
- “哪些数据不得进入模型，保存多久，如何删除？”

### 5. 编排、边界与人审

- “任务如何拆分、路由、重试、停止和失败回跳？”
- “预算用完时如何停止或降级？”
- “哪些动作必须人审，人工看什么证据？”
- “发生越权、误发或错误执行时如何隔离、回滚和追责？”

### 6. 评测与可观测性

- “标准答案、样本、指标、分母、基线和阈值是什么？”
- “谁标注、谁验收，指标冲突如何决策？”
- “一次任务能否追到模型、Prompt、资料、工具和人工修改？”
- “Bad Case 如何分类，修复后如何进入回归和发布判断？”

### 7. vibe coding 原型

- “现在能否启动原型并完成一次 P0 任务？”
- “调用的是真实工具/API、受控模拟，还是写死的演示？”
- “成功、边界和失败样本留下了哪些输入输出与日志？”
- “失败时是否诚实展示错误、降级或人工接管？”
- “原型暴露了什么文档未想到的问题，改了什么？”

### 8. 成本、上线与 Ownership

- “单次任务的模型、检索、工具、人工与存储成本如何估算？”
- “时延、并发、稳定性和合规到什么门槛才可试点？”
- “灰度、监控、停止、回滚和事故责任如何定义？”
- “哪三项关键判断由你主导，AI 的架构或代码如何验证？”
- “关掉 AI 后，能否解释一个失败样本为何发生、应改哪层？”

## MVP Harness 七项硬门

任何一项完全缺失都构成当前阶段阻断；“后续会补”不能通过。

| 门槛 | 最低通过证据 |
| --- | --- |
| **Task Spec** | 真实任务的目标、输入、输出、成功条件和不做项明确 |
| **Plan-Execute-Verify** | 计划、执行、结果校验可观察；校验失败会阻断交付 |
| **Tool/API Access** | 至少一个关键工具/API 真实可用，或有受控模拟及替换条件 |
| **Permission/Human Review** | 最小权限、人工确认点、最终责任人和禁止动作明确 |
| **Trace/Run Record** | 一次运行可追到任务、版本、节点输入输出、工具结果、人工修改和耗时 |
| **Result Verification** | 有标准答案或可执行验收规则，能判定结果是否通过 |
| **Failure Capture** | 失败被记录、分类，并有回跳/接管与重跑条件 |

## ICTSOEVMG Harness 九要素评分

分档：0 分无正文或证据；1 分只有名词、清单或计划；2 分已有机制和部分证据，但异常、恢复、评测或真实运行不完整；3 分机制可执行，成功与失败都有运行、Trace、验收和回归证据。设计但未运行的层最高 2 分。

## 用户体验五层检查

| 层级 | PRD 与原型最低检查 |
| --- | --- |
| 战略层 | 目标用户、核心任务、AI 必要性、成功指标和风险接受标准一致 |
| 范围层 | P0、非目标，以及 AI、规则、工具和人工的责任边界明确 |
| 结构层 | 主任务、分支、状态、失败恢复和人工接管能用样本走通 |
| 框架层 | 界面与导航能呈现进度、来源、澄清、确认、修改和接管入口 |
| 表现层 | 视觉与文案不掩盖不确定性，能清楚表达置信度、风险和下一步动作 |

使用一张双框架缺口表连接两者：`P0 节点 -> 用户体验层 -> Harness 要素 -> 现有证据 -> 缺口/风险 -> 修订与验证`。不要输出两份互不关联的长报告。

## 四个闭环

链路文字和顺序不得改写：

- 任务闭环：`识别 -> 查询 -> 检索 -> 审核 -> 初稿 -> 发送`
- 上下文闭环：`选择 -> 压缩 -> 保存 -> 人工接管 -> 恢复`
- 工具闭环：`选择 -> 参数校验 -> 执行 -> 异常处理`
- 评估闭环：`标准答案 -> 指标阈值 -> 离线测试 -> 失败分类 -> 回归集 -> Prompt/RAG/Harness更新`

必须用失败样本检查四条链。每个断点写明失败现象、停在哪一步、谁接管、如何恢复、修复对象、重跑条件和回归结果。

## vibe coding 最低标准

目标不是还原完整产品，而是让一条 P0 主链真实接收输入、执行规则/模型/工具、输出结果、暴露错误并留下运行记录。

最低证据：

- 可复现的启动命令或步骤、代码版本与依赖说明。
- 至少一个关键工具/API 真实接入；不能接入时明确受控模拟边界和替换条件。
- 一个成功样本、一个边界样本和一个失败样本的原始输入输出。
- Trace、截图、耗时、错误信息和人工接管记录。
- 原型暴露的问题，以及据此回改的 PRD 内容。

硬编码页面、静态演示数据、只展示截图或吞掉错误，都不能算可跑原型。

## 默认产物：导师主持提纲

使用通用方法论的默认顺序，并针对第三阶段填充：

1. **会议目标**：最多 3 条，确认产品五层、Harness、原型运行与阶段结论。
2. **阶段与预判**：一句话给阶段判据、已有证据、最大阻断和预判。
3. **60 分钟会议执行表**：只使用本文件的五个时间盒；把主持提示、导师判断和教学内容合并在表内。
4. **PRD 完整性与双框架缺口表**：先保留目标、范围、Workflow、角色、功能、AI I/O、数据权限、验收和原型运行的完整性判断；再列最多 3 条影响 P0 交付、验证或风险边界的双框架缺口。涉及 Agent 时，补 `System Boundary + 控制模式 + Agent 拓扑` 的判型依据，再把判型缺口并入对应 Harness 层；没有运行证据时直接标记阻断。
5. **当场结论与会后任务**：阶段结论、P0 修订、最多 3 项重跑任务、验收证据和下一阶段条件。

不要默认生成逐章 PRD 评估或九层长报告；把评分和判断转成导师在第五、第六环节需要讲清的内容。

## 显式产物：评估报告骨架

仅当用户明确要求书面评估报告时，严格按以下顺序输出：

1. **结论**：推进 / 收束 / 换题或重做；一句话判据与硬阻断项。
2. **已扎实部分**：业务范围、系统机制、原型运行、评测风险和本人判断。
3. **完整性检查**：目标/范围、Workflow、角色/状态、AI I/O、数据资产、评测门槛、可跑原型；列证据、缺口与判断。
4. **关键问题**：只列 1-3 个最大问题；写证据、影响、修复动作与验收方式。
5. **AI能力与架构问题**：主原型、规则/RAG/LLM/Agent/工具/人审分工、状态编排、Agent 判型、数据/时延/成本取舍；判型证据不足时明确降级或待验证。
6. **Harness门槛**：七项逐条给证据、通过/阻断与补齐动作。
7. **九层评分**：使用固定表头和九层原名，不把计划算实现。
8. **四个闭环**：逐条写当前链路、断点、接管、恢复与回归。
9. **认知偏误**：偏误、作业表现、点破与修正。
10. **Now-Next-Later**：Now 只放阻断真实交付或风险红线的事项。
11. **当面追问**：问题及合格回答应包含的证据。
12. **AI PM结论**：已证明、尚不能证明、本人关键决策与进入下一阶段的条件。

## 阶段交付门槛

- 原有 PRD 完整性审核已完成，目标、范围、流程、功能、角色、AI I/O、数据权限、验收和原型证据没有被 Agent 判型替代。
- 业务问题、目标、P0 与非目标一致。
- Before / After Workflow 能用真实样本走通。
- 角色、权限、状态、超时、回退与恢复明确。
- 关键 AI 节点有输入、输出、Schema、校验、异常和 fallback。
- 涉及 Agent 的方案能写清 System Boundary、控制模式、Agent 拓扑及 Next Action、Replanning、Termination 证据；Multi-Agent 另有独立边界、专业分工和协调证据。
- 数据、知识、规则资产可追溯、可更新、可控权。
- MVP Harness 七项全部有证据。
- vibe coding 原型能启动并跑通成功、边界与失败三类样本。
- 九层按 0-3 分评分，设计与运行证据分开。
- 四个闭环的断点已经分级和指派修复动作。
- 评测集、指标、分母、基线、阈值、标注人与回归集明确。
- 成本、时延、隐私、合规、灰度、停止与回滚条件明确。
- 学员能讲清三项本人决策、被否方案及证据。
