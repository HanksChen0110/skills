# AI PM 陪跑通用方法论

本文件是三个阶段共同使用的主持与判断标准。默认服务于导师开会，不默认生成学员评估报告。先看证据，再给判断；章节、术语和计划都不能自动算作实现。

## 双模式产出协议

### 默认主持提纲

默认产物必须帮助导师完成一场 60 分钟会议，而不是把学员材料重新整理成一篇长报告。固定包含：

1. 会议目标。
2. 阶段与预判。
3. 60 分钟会议执行表。
4. 阶段核心产物。
5. 当场结论与会后任务。

会议执行表只写导师需要看、听、判断和讲解的内容，不写成逐字稿，不替学员完成作业。主持提示与知识讲解合并到对应环节，不再另写重复章节。根据材料已有证据做针对性填充；没有证据时明确写“会前待补”或“会上待确认”。

默认篇幅目标为 1500-2200 个中文字符，材料简单时更短。会议目标最多 3 条；每个环节最多 1 个关键追问和 1 个主要教学点；关键缺口、阶段核心发现、会后任务各最多 3 项。只有会影响本次判断的材料缺失才列出，不复述完整作业目录和背景，不输出现场话术、空白模板或框架百科。

第一周按 `stage1-direction.md` 的“第一周必备教学内容”执行例外：三类岗位、三个意识、完整 Harness 九要素和 Local First 必须实际出现在材料正文中；不受三项上限、单环节一个教学点或字数目标限制。内容集中写一次，会议表只写讲解安排和项目应用；缺业务证据只影响项目判断，不影响这些通用教学内容的输出。

### 显式评估报告

只有用户明确要求书面评估报告时，才使用阶段文件末尾的报告骨架。报告模式也必须遵守事实、观察、推测、决策和缺失分离，不得反向成为默认输出。

## 业务边界与 AI 导师责任

导师不需要成为学员所在行业的专家，也不冒充行业专家。业务内容只承担一个作用：为 AI 产品判断提供真实约束。

### 可以确认的业务事实

- 谁发起任务、谁使用结果、谁审核、谁承担最终责任。
- 当前任务从什么输入开始，以什么输出和验收结束。
- 哪一步存在模糊判断、非结构化信息、变化频繁或高人工成本。
- 有哪些真实样本、数据、知识、规则、工具、权限和风险限制。
- 错误一次会造成什么后果，哪些动作不可自动执行。

### 不应代替学员回答的内容

- 行业规则、业务数字、用户偏好和政策要求的具体结论。
- 没有样本或来源支撑的业务流程、收益预测和优先级。
- 看似合理但未核验的行业解决方案。
- 由业务负责人决定的责任、例外和风险接受标准。

遇到业务不熟悉时，先让学员提供事实，再把事实转换为 AI 产品问题：是否适合 AI、需要什么 Context、规则与模型怎么分工、结果如何验证、失败如何接管、成本和风险是否可接受。无法确认的业务结论统一标记“需学员或业务专家确认”。

## AI 技术初选与阶段衔接

技术选择必须从真实业务流程节点、任务特征和可用证据出发，不从技术名词反推场景。逐节点按以下顺序判断：

1. 逻辑确定、条件稳定时，优先使用规则或普通系统。
2. 步骤固定、无需根据中间结果动态规划时，优先使用 Workflow。
3. 需要理解、抽取、分类或生成文本时，考虑 NLP/LLM。
4. 需要引用企业知识、专业资料或可追溯依据时，考虑 RAG；能用结构化查询解决时不强行使用 RAG。
5. 需要处理图片、音频、视频或图纸时，考虑多模态模型、OCR 或 ASR。
6. 需要预测、分类、评分或异常检测时，比较传统机器学习、深度学习和时序模型，不默认使用 LLM。
7. 只有任务需要跨工具动态规划，并会根据中间结果改变后续路径时，才考虑 Agent；固定链路继续使用 Workflow。
8. 高风险结论或执行动作必须增加人工确认、权限控制、停止条件和审计，不由 AI 独立决定。

如果普通系统、规则或人工更合适，明确写“无需 AI”。每项 AI 建议至少说明对应流程节点、任务输入输出、选择理由、所需数据或知识、人工边界和验证动作；证据不足时标为“候选，待验证”，不得包装成已经确定的架构。

阶段职责如下：

- **第一阶段**：根据业务流程完成技术初选和方法教学，形成候选技术适配表。
- **第二阶段**：通过竞品证据、统一样本和能力边界测试验证初选，允许推翻第一阶段建议。
- **第三阶段**：将验证后的选择细化为架构、Context、Tool、输入输出 Schema、评测、失败处理、成本和治理要求。

后续阶段没有验证证据时，不得因为第一阶段写过某项技术就直接继承为最终方案。

## 合并会议执行卡

会议执行表固定四列，每格最多两句：

1. **时间与环节**：本段时长和唯一目标。
2. **学员要讲清**：必须提供的事实、判断或证据；必要时附一个关键追问。
3. **导师判断与讲解**：先写判断，再补一个与当前缺口直接相关的 AI 机制或取舍。
4. **通过条件/未通过处理**：先写可观察的通过条件；未达到时写降级、待补或阻断动作。

进入条件必须可判断。禁止写“基本清楚”“大致合理”等模糊表述；改成“能用一个样本走通”“能明确 I/O 和责任人”“能指出来源与版本”等可观察条件。

第一周先覆盖规定的四组必备教学内容；第二、三阶段只选择与当前最大缺口直接相关的 2-3 个主题。教学安排嵌入会议执行卡的“导师判断与讲解”，优先结合 AI 适配、规则/Workflow/LLM/RAG/Agent/Tool/人工分工、Context、状态与编排、结构化输出、失败与人审、验证与 Bad Case、Trace、成本和权限。

## ICTSOEVMG Harness 九要素

统一分档：

- **0 分**：没有正文或证据。
- **1 分**：只有名词、清单、页面或计划，机制无法执行。
- **2 分**：主机制已经定义并有部分证据，但异常、恢复、真实运行、评测或治理仍不完整。
- **3 分**：正常与失败路径均可执行，有运行、Trace、验收、接管和回归证据。

第一周用它显化架构意识，完整介绍九要素及其问题，暂不要求九项全部实现或评分；第二阶段用它建立竞品观察坐标，第三阶段用它约束 PRD 与原型。需要评分时必须使用以下名称，不得改写：

### Interaction 交互

- 用 User Intent、Task Spec、Output Contract、Channel Adapter 管理用户如何发起、澄清、确认、查看状态、接收结果和完成验收。
- 常见缺失：只有入口和结果页，没有澄清、状态、人工确认、失败反馈与交付完成标准。
- 3 分证据：成功、澄清、失败、接管、恢复和验收均能在原型或测试中走通。

### Context 上下文

- 通过项目指令加载、检索、记忆注入、压缩和隔离，管理模型每一步看见的业务事实、历史、规则与临时信息。
- 常见缺失：只列输入材料，不处理冲突、窗口超限、跨用户隔离和接管后的恢复。
- 3 分证据：来源、选择、压缩、隔离、版本、持久化和恢复均有规则与样本验证。

### Tool 工具

- 用 Tool Registry、Schema、MCP Client 和权限策略管理工具选择、参数校验、执行、结果归一化、错误码、超时和降级。
- 常见缺失：只列工具名，没有可执行 Schema、真实接口、最小权限和统一返回结构。
- 3 分证据：真实调用能展示输入输出、权限、异常、归一化和日志。

### State / Memory 状态记忆

- 管理会话状态、任务状态、产物存储和长期记忆的写入、更新、过期、回退与恢复。
- 常见缺失：只有状态名或数据库字段，没有进入退出条件、快照、超时和失败回跳。
- 3 分证据：状态机、生命周期、快照、回退和恢复均通过成功与失败测试。

### Orchestration 编排

- 用 ReAct Loop、Planner-Executor、子 Agent 调度和停止条件管理任务分解、依赖、路由、预算、重试、回跳和人工恢复。
- 常见缺失：只有理想流程图，或为简单固定流程强行使用复杂 Agent。
- 3 分证据：关键分支、预算、重试、停止、回跳和接管都可执行并经过失败验证。

### Execution 执行沙箱

- 用容器、文件系统与网络策略、审批闸门管理模型和工具可读写的数据、系统、密钥及高风险动作。
- 常见缺失：只写“只读”或“人工确认”，没有白名单、沙箱、密钥边界和事故恢复。
- 3 分证据：最小权限、隔离、审批、审计、回滚和事故恢复均可测试。

### Verification 验证

- 用测试、Linter、Schema 校验和 LLM-as-Judge 管理标准答案、指标、阈值、失败分类、回归与发布门槛。
- 常见缺失：只有指标名称或目标数字，没有样本、分母、标注、基线和回归。
- 3 分证据：评测集、标注、阈值、失败分类、回归和版本决策形成完整记录。

### Monitoring 可观测

- 用 Trace、Span、Token 成本和 Replay 管理任务 ID、模型/Prompt、工具输入输出、资料版本、耗时和失败原因。
- 常见缺失：只说“记录日志”，无法解释或重放一次任务。
- 3 分证据：端到端 Trace 可定位、重放、比较版本并把失败送入 Bad Case 回归。

### Governance 治理

- 用策略引擎、权限控制、审计日志和限流管理隐私、人工责任、内容安全、例外、规则变更和事故处置。
- 常见缺失：只有风险清单，没有负责人、阻断条件、审计和事故演练。
- 3 分证据：风险分级、权限、数据治理、人工责任、审计、例外和事故流程均已验证。

## 用户体验五层

第二、三阶段必须同时从产品侧检查五层，但只展开会改变决策的层；缺少证据时写“未知”或“本阶段不展开”。

| 层级 | 要判断什么 | 与 Harness 的连接 |
| --- | --- | --- |
| 战略层 | 为谁解决什么问题，为什么需要 AI，用什么结果证明价值 | Interaction、Verification、Governance |
| 范围层 | P0 做什么、不做什么，哪些由 AI、规则、工具或人工承担 | Tool、Execution、Governance |
| 结构层 | 用户任务怎样流转，信息怎样组织，AI、工具和人工如何协作 | Context、State / Memory、Orchestration |
| 框架层 | 界面、导航、信息呈现、状态反馈、澄清、确认和接管如何安排 | Interaction、State / Memory、Monitoring |
| 表现层 | 视觉、文案和反馈怎样表达置信度、来源、风险与下一步动作 | Interaction、Verification、Governance |

双框架不是两份独立报告。用户体验五层回答“产品如何被理解和使用”，Harness 九要素回答“AI 系统如何被约束、执行和验证”；最终必须合并成对学员自己产品的节点、边界和 P0 取舍。

## 四个闭环

链路文字与顺序固定，不得改写。闭合不仅是走到最后，还要有逐步验收、失败回跳、人工接管、恢复和可追溯证据。

### 任务闭环

`识别 -> 查询 -> 检索 -> 审核 -> 初稿 -> 发送`

每一步都要有输入、负责人、成功标准和失败路径；发送前有验收，发送后能确认交付完成。

### 上下文闭环

`选择 -> 压缩 -> 保存 -> 人工接管 -> 恢复`

能说明选什么、舍弃什么、如何压缩、接管前保存什么，以及人工处理后如何恢复任务。

### 工具闭环

`选择 -> 参数校验 -> 执行 -> 异常处理`

选择有条件、执行前校验参数、结果被标准化；异常对应重试、降级或人工接管，并保留权限和日志。

### 评估闭环

`标准答案 -> 指标阈值 -> 离线测试 -> 失败分类 -> 回归集 -> Prompt/RAG/Harness更新`

失败必须进入分类与回归集，更新后重跑同一基准；只收反馈、不更新和回归，不算闭合。

## 认知偏误

| 偏误 | 典型表现 | 点破方式 |
| --- | --- | --- |
| 目录完整偏误 | 章节和术语齐全，就认为方案成熟；关键机制、评测或失败路径仍为空 | 随机抽一章，要求给出样本、字段、阈值与运行证据 |
| 规划谬误 | 多接口、多角色、多模态、多工具和多端一起进入 P0，却没有资源与周期估算 | 逐项写依赖、负责人、验证时间和失败概率，三周不能留证据的移出 P0 |
| 方案先行偏误 | 用户、接口、数据和权限尚未确认，就先确定 Agent、RAG 和完整架构 | 每个结论前写已知事实、待验证假设、验证动作与决策影响 |
| AI中心偏误 | 默认每个节点都由模型处理，忽略规则、结构化查询、现有系统和人工责任 | 逐节点比较规则、普通系统、人工与 AI，找出真正需要不确定性处理的部分 |
| 虚假精确 | 写出漂亮比例，却没有分母、样本、标注人、基线和阈值来源 | 改写成指标定义、分母、样本、基线、阈值来源与决策用途；补不出就降为假设 |

## Now / Next / Later

- **Now**：不补就无法验证主链价值、守住风险红线或进入下一阶段；三周内必须形成样本、原型、测试、日志或明确规则。
- **Next**：P0 证明价值后再做，用于扩大覆盖、提高稳定性、性能或正式接入；通常依赖真实试用数据。
- **Later**：平台化、组织级治理、复杂多 Agent、多模型路由和全量自动化等当前不需要的规模化建设。

分级纪律：

1. 先问“不做它，主链还能否完成一次可验收交付”。
2. 只有答案为“不能”的能力才可能进入 Now。
3. 每个 Now 必须写验证证据和完成条件；写不出就降级。
4. 新增一个 P0 项，必须同步移出一个非必要项。
5. 主持提纲或报告中明确记录不做项，后续不能以“更完整”为由悄悄加回。

## 追问纪律

追问优先级依次为：AI 选择依据、节点 I/O、Context/工具/人审分工、失败路径、评测证据、Ownership。业务问题仅用于补足这些判断所需的事实，不延伸成行业咨询。

### 要细节

- “把这一步拆开讲：谁在什么入口，拿到什么输入，做了什么动作，得到什么输出？”
- “系统具体在哪个节点判断，判断前后分别发生什么？”
- “正常路径讲完了，失败后从哪里回跳，谁接手？”
- “请拿一个真实样本走完整条链，不要只讲概念。”

### 要数字

- “这个比例的分母是什么，统计了多少样本、什么周期？”
- “当前基线是多少，目标值为什么设在这里？”
- “一次任务的时延、Token、人工复核时间和成本分别是多少？”
- “到什么阈值会推进、暂停或停止，由谁确认？”

### 要反例

- “什么情况下这套方案一定不适用？”
- “给一个模型看似答对、实际必须拦截的例子。”
- “哪类用户或数据会让你的结论失效？”
- “如果竞品采用相反做法，它可能基于什么合理约束？”

### 要决策依据

- “为什么选 A，而不是规则、普通 Workflow、人工或 B 方案？”
- “这条结论来自事实、测试，还是推测？”
- “哪个证据真正改变了你的 P0？”
- “资源减半时保留什么、放弃什么，依据是什么？”

每次只追一个事实缺口；拿到可验证回答后再进入下一层。学员说出技术名词时，继续追使用节点、输入输出、失败处理、评测和责任人。学员无法提供业务事实时，记录待确认项，不由导师或 AI 补写答案。

## AI 协作比例追问

固定问：

1. “这份作业从开始到提交，具体怎么完成？”
2. “人和 AI 各占多少？按研究、判断、写作、画图、验证分别说。”
3. “哪三项关键判断由你完成，AI 哪些建议被你否掉？”
4. “你怎样验证 AI 生成的事实、架构、指标与结论？”
5. “关掉 AI 后，能否用一个真实样本讲清主 Workflow、边界和取舍？”

健康信号：AI 负责检索、发散、结构化、草拟和候选方案；学员负责定义问题、核验事实、做取舍、收束 P0 和承担结论，并能展示 AI 错误及修订记录。

警惕信号：只说“AI 写、我审核”，却说不出审核标准；把模型推测当事实；文档完整但无法解释节点、失败和边界；一被追问就无法重建推理链。
