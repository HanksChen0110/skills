# AI PM 陪跑通用方法论

本文件是三个阶段共同使用的判断标准。先看证据，再给分数；章节、术语和计划都不能自动算作实现。

## 九层 Harness

统一分档：

- **0 分**：没有正文或证据。
- **1 分**：只有名词、清单、页面或计划，机制无法执行。
- **2 分**：主机制已经定义并有部分证据，但异常、恢复、真实运行、评测或治理仍不完整。
- **3 分**：正常与失败路径均可执行，有运行、Trace、验收、接管和回归证据。

逐层评分时必须使用以下名称，不得改写：

### Interaction 任务交互

- 管理用户如何发起、澄清、确认、查看状态、接收结果和完成验收。
- 常见缺失：只有入口和结果页，没有澄清、状态、人工确认、失败反馈与交付完成标准。
- 3 分证据：成功、澄清、失败、接管、恢复和验收均能在原型或测试中走通。

### Context 上下文

- 管理业务事实、历史、规则、偏好和临时信息的来源、选择、压缩、隔离、保存与恢复。
- 常见缺失：只列输入材料，不处理冲突、窗口超限、跨用户隔离和接管后的恢复。
- 3 分证据：来源、选择、压缩、隔离、版本、持久化和恢复均有规则与样本验证。

### Tool 工具

- 管理工具选择、参数校验、执行、权限、结果归一化、错误码、超时和降级。
- 常见缺失：只列工具名，没有可执行 Schema、真实接口、最小权限和统一返回结构。
- 3 分证据：真实调用能展示输入输出、权限、异常、归一化和日志。

### Memory / State 记忆与状态

- 管理任务状态、阶段产物、历史决策和偏好的写入、更新、过期、回退与恢复。
- 常见缺失：只有状态名或数据库字段，没有进入退出条件、快照、超时和失败回跳。
- 3 分证据：状态机、生命周期、快照、回退和恢复均通过成功与失败测试。

### Orchestration 编排

- 管理任务分解、依赖、顺序、路由、并发、预算、重试、停止、回跳和人工恢复。
- 常见缺失：只有理想流程图，或为简单固定流程强行使用复杂 Agent。
- 3 分证据：关键分支、预算、重试、停止、回跳和接管都可执行并经过失败验证。

### Execution / Sandbox 执行边界

- 管理模型和工具可读写的数据、文件、网络、系统、密钥，以及高风险动作的隔离和授权。
- 常见缺失：只写“只读”或“人工确认”，没有白名单、沙箱、密钥边界和事故恢复。
- 3 分证据：最小权限、隔离、审批、审计、回滚和事故恢复均可测试。

### Evaluation / Feedback 评测反馈

- 管理标准答案、指标、阈值、离线测试、线上反馈、失败分类、回归与发布门槛。
- 常见缺失：只有指标名称或目标数字，没有样本、分母、标注、基线和回归。
- 3 分证据：评测集、标注、阈值、失败分类、回归和版本决策形成完整记录。

### Observability 可观测性

- 管理任务 ID、模型/Prompt、工具输入输出、资料版本、规则命中、人工修改、耗时、成本和失败原因。
- 常见缺失：只说“记录日志”，无法解释或重放一次任务。
- 3 分证据：端到端 Trace 可定位、重放、比较版本并把失败送入 Bad Case 回归。

### Governance / Safety 治理安全

- 管理隐私、RBAC、留存删除、人工责任、内容安全、审计、例外、规则变更和事故处置。
- 常见缺失：只有风险清单，没有负责人、阻断条件、审计和事故演练。
- 3 分证据：风险分级、权限、数据治理、人工责任、审计、例外和事故流程均已验证。

## 四个闭环

链路文字与顺序固定，不得改写。闭合不仅是走到最后，还要有逐步验收、失败回跳、人工接管、恢复和可追溯证据。

### 任务闭环

`识别 -> 查询 -> 检索 -> 审核 -> 初稿 -> 发送`

每一步都要有输入、负责人、成功标准和失败路径；发送前有验收，发送后能确认交付完成。

### 上下文闭环

`选择 -> 压缩 -> 保存 -> 人工接管 -> 恢复`

能说明选什么、舍弃什么、如何压缩、接管前保存什么，以及人工处理后如何恢复任务。

### 工具闭环

`选择 -> 参数校验 -> 执行 -> 异常处理`

选择有条件、执行前校验参数、结果被标准化；异常对应重试、降级或人工接管，并保留权限和日志。

### 评估闭环

`标准答案 -> 指标阈值 -> 离线测试 -> 失败分类 -> 回归集 -> Prompt/RAG/Harness更新`

失败必须进入分类与回归集，更新后重跑同一基准；只收反馈、不更新和回归，不算闭合。

## 认知偏误

| 偏误 | 典型表现 | 点破方式 |
| --- | --- | --- |
| 目录完整偏误 | 章节和术语齐全，就认为方案成熟；关键机制、评测或失败路径仍为空 | 随机抽一章，要求给出样本、字段、阈值与运行证据 |
| 规划谬误 | 多接口、多角色、多模态、多工具和多端一起进入 P0，却没有资源与周期估算 | 逐项写依赖、负责人、验证时间和失败概率，三周不能留证据的移出 P0 |
| 方案先行偏误 | 用户、接口、数据和权限尚未确认，就先确定 Agent、RAG 和完整架构 | 每个结论前写已知事实、待验证假设、验证动作与决策影响 |
| AI中心偏误 | 默认每个节点都由模型处理，忽略规则、结构化查询、现有系统和人工责任 | 逐节点比较规则、普通系统、人工与 AI，找出真正需要不确定性处理的部分 |
| 虚假精确 | 写出漂亮比例，却没有分母、样本、标注人、基线和阈值来源 | 改写成指标定义、分母、样本、基线、阈值来源与决策用途；补不出就降为假设 |

## Now / Next / Later

- **Now**：不补就无法验证主链价值、守住风险红线或进入下一阶段；三周内必须形成样本、原型、测试、日志或明确规则。
- **Next**：P0 证明价值后再做，用于扩大覆盖、提高稳定性、性能或正式接入；通常依赖真实试用数据。
- **Later**：平台化、组织级治理、复杂多 Agent、多模型路由和全量自动化等当前不需要的规模化建设。

分级纪律：

1. 先问“不做它，主链还能否完成一次可验收交付”。
2. 只有答案为“不能”的能力才可能进入 Now。
3. 每个 Now 必须写验证证据和完成条件；写不出就降级。
4. 新增一个 P0 项，必须同步移出一个非必要项。
5. 报告中明确记录不做项，后续不能以“更完整”为由悄悄加回。

## 追问纪律

### 要细节

- “把这一步拆开讲：谁在什么入口，拿到什么输入，做了什么动作，得到什么输出？”
- “系统具体在哪个节点判断，判断前后分别发生什么？”
- “正常路径讲完了，失败后从哪里回跳，谁接手？”
- “请拿一个真实样本走完整条链，不要只讲概念。”

### 要数字

- “这个比例的分母是什么，统计了多少样本、什么周期？”
- “当前基线是多少，目标值为什么设在这里？”
- “一次任务的时延、Token、人工复核时间和成本分别是多少？”
- “到什么阈值会推进、暂停或停止，由谁确认？”

### 要反例

- “什么情况下这套方案一定不适用？”
- “给一个模型看似答对、实际必须拦截的例子。”
- “哪类用户或数据会让你的结论失效？”
- “如果竞品采用相反做法，它可能基于什么合理约束？”

### 要决策依据

- “为什么选 A，而不是规则、普通 Workflow、人工或 B 方案？”
- “这条结论来自事实、测试，还是推测？”
- “哪个证据真正改变了你的 P0？”
- “资源减半时保留什么、放弃什么，依据是什么？”

每次只追一个事实缺口；拿到可验证回答后再进入下一层。学员说出技术名词时，继续追使用节点、输入输出、失败处理、评测和责任人。

## AI 协作比例追问

固定问：

1. “这份作业从开始到提交，具体怎么完成？”
2. “人和 AI 各占多少？按研究、判断、写作、画图、验证分别说。”
3. “哪三项关键判断由你完成，AI 哪些建议被你否掉？”
4. “你怎样验证 AI 生成的事实、架构、指标与结论？”
5. “关掉 AI 后，能否用一个真实样本讲清主 Workflow、边界和取舍？”

健康信号：AI 负责检索、发散、结构化、草拟和候选方案；学员负责定义问题、核验事实、做取舍、收束 P0 和承担结论，并能展示 AI 错误及修订记录。

警惕信号：只说“AI 写、我审核”，却说不出审核标准；把模型推测当事实；文档完整但无法解释节点、失败和边界；一被追问就无法重建推理链。
