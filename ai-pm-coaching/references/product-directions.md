# 产品方向识别与能力拼图

本文件服务第一至第三阶段的主持提纲与书面评估。按主要任务识别方向，再读取命中项；产品方向回答“做哪类系统”，Harness 回答“系统如何可靠运转”，用户体验五层回答“为什么做、做什么、如何组织和呈现”，三者不互相替代。

## 识别与使用规则

- 先看任务发起人、真实输入、关键判断/动作、交付结果与验收方式，不按“RAG”“Agent”等技术名词归类。流程不清先请学员讲一个真实样本，不替其编造业务事实。
- 混合项目按主要验收结果定主方向，其他列为辅助能力。例如审查后生成统计报表仍可主归审查系统、辅以 ChatBI；只有查指标问数是主任务时才主归 ChatBI。证据无法区分时标记候选方向及关键待确认项。
- 以下组合是导师采用的参考产品框架，不是行业强制标准，也不是固定执行顺序。完整核对各拼图，按真实需求判断 P0、后续或不适用并说明理由；不要求全量实现，不把“材料没写”直接判成“产品没有”。
- 未命中五类时不硬套：按真实任务比较 AI 与非 AI 路径，提炼该项目的能力组合；技术可行性不清时再做针对性调研，区分来源事实、推断和待验证方案，不能把未调研称为已证实。
- 归类后仍需独立判断 AI 适配、数据条件、错误代价与人工边界；框架匹配不构成可行性或实现证明。

## 五类参考框架

### 1. 审查系统

**识别信号**：主要交付是对材料或行为给出规则符合性、风险项、处理建议及复核结论，而不是仅做摘要或统计。

**参考组合**：规则引擎 + 语义审查 + RAG 政策库 + 人工复核 + AIGC + ChatBI。

- 规则引擎：确定性条件、阈值与规则版本是否明确，能否解释命中原因。
- 语义审查：需模型理解的内容是什么，规则与模型结论冲突时怎样处理；用漏报、误报样本验证。
- RAG 政策库：政策来源、适用范围、生效版本和引用位置是否可核验；无依据或版本冲突时不能强判。
- 人工复核：谁复核、什么触发、如何记录修订；高风险结论保留审批边界。
- AIGC：用于审查说明、整改建议或报告草稿；核对生成内容与证据一致，不替代审查判定。
- ChatBI：有审查统计与问数需求时核对指标口径、数据权限和可追溯计算；无此需求可列后续或不适用，不影响核心审查闭环。

### 2. ChatBI

**识别信号**：主要任务是用自然语言查询结构化业务数据，交付可核验的指标、表格或图表及解释。

**参考组合**：指标字典 + Text2SQL + 权限控制 + AIGC 解读。

- 指标字典：指标定义、维度、时间口径和数据表关联是否清楚；歧义先澄清，不让模型自定口径。
- Text2SQL：是否有 Schema 上下文、SQL 校验、只读执行和结果核对；用已知答案验证关联、聚合与时间过滤，不只看 SQL 能运行。
- 权限控制：身份、表/行/列权限是否在执行端生效；跨权限请求不能只靠提示词拒绝。
- AIGC 解读：解释能否回到查询结果，区分事实、推测和因果；数值错误不能靠流畅文案掩盖。

### 3. 多模态知识助理

**识别信号**：主要任务是读懂文档、扫描件或图文资料，交付基于材料的问答、提取或总结。

**参考组合**：OCR/文档解析 + RAG + AIGC 总结 + 人工确认。

- OCR/文档解析：按实际输入选择 OCR 或结构解析，检查表格、图片、版面和页码保留；数字原生文本不强加 OCR。
- RAG：切分、检索和引用是否保留来源位置；测试跨页信息、相似版本与无答案情况。
- AIGC 总结：是否忠于原文并标记缺失或冲突；用原文逐项核对关键事实。
- 人工确认：明确关键字段、低质量解析或重要结论的确认点，修订能否回到原始材料。

### 4. 销售质检/陪练

**识别信号**：围绕销售沟通过程评估表现、发现问题或练习改进；需先区分事后质检与交互陪练。

**参考组合**：ASR/OCR + 规则评分 + RAG 话术库 + AIGC 复盘。

- ASR/OCR：音频用 ASR、截图用 OCR、原生文字直接解析；核对说话人、时间戳或原文位置，避免转录错误造成误判。
- 规则评分：评分维度、证据片段、权重与人工标注口径是否明确；检查重复评测稳定性和与人工评分的差异。
- RAG 话术库：话术适用场景、版本和依据是否明确，不能把检索到的话术都当标准答案。
- AIGC 复盘：建议须对应具体对话证据和可执行练习，不能泛泛评价销售能力。
- 若确为交互陪练，另核对情境/客户角色、多轮状态与结束条件；若仅质检，不强加模拟对话能力。

### 5. 企业知识 Agent

**识别信号**：主要任务不仅查知识，还需结合企业工具完成多步工作并交付可确认的动作结果；仅问答不自动认定需要 Agent。

**参考组合**：RAG + 工具调用 + Workflow + 权限 + 引用溯源。

- RAG：知识来源、更新机制、检索边界和无答案处理是否清楚。
- 工具调用：输入输出契约、执行结果、失败反馈是否明确；外部写入的审批与重复执行保护按动作风险设计。
- Workflow：节点、状态、分支、停止条件和失败恢复是否明确；固定流程足够时不强加自主规划或多 Agent。
- 权限：检索与动作均受用户身份和资源权限约束，审批发生在实际执行前。
- 引用溯源：知识结论能回到来源，动作结论能回到工具结果与运行记录；不能用知识引用冒充动作成功证据。

## 三阶段怎样落地

| 阶段 | 框架用途 | 最小证据与输出 |
| --- | --- | --- |
| 第一阶段：方向确认 | 识别主方向；判断哪些节点值得 AI 化、哪些拼图支撑最小闭环 | 真实样本与现有流程；给 AI 适配结论、候选能力组合、关键缺口与最低成本验证，不要求已有系统 |
| 第二阶段：竞品分析 | 将拼图转为统一测试维度，验证能力边界与自己产品的取舍 | 同任务、同输入的试用记录及来源；记录实际表现与未知，不从界面表现推定内部架构，也不因竞品没展示而认定没有 |
| 第三阶段：PRD 与原型 | 把 P0 拼图落到节点、数据、接口、权限、失败路径与验收 | 区分设计说明与运行结果；逐项核对适用 P0 能力的成功、失败及人工接管证据，给修订动作与回归验收 |

第二阶段优先测试会改变自己产品决策的拼图，而非重做方向课或列技术名词。可从上述检查点选一个正常样本和一个关键异常样本；没有可比测试时输出测试计划，不伪造竞品结论。公开文档只能证明其披露的内容，测试结果也只代表对应版本与条件下的表现。

## 输出收敛

阶段预判写“主方向/候选方向 + 归类依据”，必要时补辅助能力；未归类写缺少哪项事实。核心产物用一行保留命中方向的完整参考组合，并简注哪些后续或不适用及理由，不展开其他四类。

将最多 3 项关键拼图缺口合入既有技术适配表或双框架表，不新增平行清单。每项包含：`拼图/真实节点 -> 现有证据与状态 -> 缺口及优先级 -> 补齐动作与验收`。状态区分“有运行证据、仅有设计、已确认缺失、材料未提供”，后者的动作是补证据，不直接要求重建。

第二、三阶段在同一行关联最相关的 Harness 要素与体验层，例如指标口径关联 Context、Verification 与战略/范围层；避免机械填写九要素乘五层的矩阵。没有项目证据时只给关键待确认项，不生成空表。第一周四组必备教学内容保持原规则，不因新增分类而删减或重复。
